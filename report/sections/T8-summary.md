# 六、实验总结与收获

## 6.1 对操作系统的理解（初稿）

物理内存管理是操作系统内核所有高级机制（虚存抽象、进程地址空间隔离、缺页异常处理、内核小对象缓存）的硬件基石。通过本实验的动手实现与分析，我们建立了从裸机物理内存抽象为离散数据结构、多策略分配回收以及硬件 MMU 协同的系统性认知：

### 1. 实验核心知识点与 OS 原理的映射对照

| 实验知识点 | 对应 OS 原理概念 | 含义、关系与设计差异分析 |
| :--- | :--- | :--- |
| **`struct Page` 描述符数组** | **物理页帧管理（Frame Management）** | **含义**：将物理内存按固定大小（4KB）切分为页帧，用内存开头的结构体数组一一跟踪每个页的状态。<br/>**关系与差异**：OS 原理中通常抽象为位图（Bitmap）或空闲链表；ucore 中采用固定尺寸数组，占用物理内存开销约占受管内存的 $0.97\%$（每 4096 字节对应 40 字节描述符），通过线性映射下表偏移完成 $O(1)$ 指针换算，较传统位图支持更丰富的引用计数（`ref`）与复合标志位（`flags`）。 |
| **First-Fit / Best-Fit 分配算法** | **连续物理内存动态分配（Contiguous Allocation）** | **含义**：在未开启按需分页机制下，为内核申请多个物理地址连续的页面。<br/>**关系与差异**：First-Fit 优先选择首个匹配块（速度较快但低位碎片集中），Best-Fit 遍历全链表寻找最小合适块（保留大块但易产生极小无法利用的外碎片）。两者在 ucore 中均通过双向循环链表实现，且**仅链接空闲块的首页节点**，释放时依赖物理地址相邻性判定执行 $O(1)$ 双向合并。 |
| **Buddy System 伙伴系统** | **二叉树指数级内存切分（Buddy Allocation）** | **含义**：以 $2^k$ 阶块为单位组织空闲内存，通过二分拆解与伙伴异或算术合并快速响应分配与释放请求。<br/>**关系与差异**：相较于 First-Fit 的 $O(N)$ 链表线性遍历，伙伴系统的分配与合并复杂度降为 $O(\log N)$ 或 $O(1)$，极大抑制了外部碎片，但会引入一定程度的内部碎片（向上取整至 2 的幂次）。 |
| **SLUB / Slab 小对象分配器** | **内核细粒度对象缓存机制（Object Caching）** | **含义**：针对内核小数据结构（数十至数百字节）的频繁申请与释放，在物理页内部划分定长对象池。<br/>**关系与差异**：OS 原理强调以页（4KB）为统一管理单位，但内核直接按页分配极小结构体将造成高达 $90\%$ 以上的内部碎片。SLUB 在单个或多个 Page 内部维护空闲单向链表，通过 `kmalloc` 动态派发，彻底消除小对象的页级空间浪费。 |
| **Sv39 分页与高半核映射** | **虚拟内存保护与多级页表（Paging & MMU）** | **含义**：利用硬件 MMU 的三级页表实现 39 位虚拟地址到 56 位物理地址的转换。<br/>**关系与差异**：操作系统通过 `va_pa_offset` 实现内核虚存空间的线性映射，使得 S 态内核能够在保护模式下自由访问受管物理内存，而无需频繁重构页表项。 |

### 2. OS 原理中核心但本实验尚未涉及的高级机制

1. **反向映射机制（Reverse Mapping, rmap）**：
   在真实操作系统（如 Linux）中，一个物理页可能同时被多个进程的虚拟页表（PTE）映射（例如动态共享库或共享内存）。当系统需要回收或换出该物理页时，必须能够从 `Page` 结构体快速反向查找到所有引用它的进程页表项并将其无效化。ucore 当前阶段仅记录了简单的引用计数 `ref`，未构建反向链表（`anon_vma` / `address_space`）。
2. **页面置换与换页机制（Page Replacement & Swapping）**：
   OS 原理中的缺页异常处理（Page Fault Handler）、LRU / Clock 页面置换算法、工作集模型（Working Set）以及交换分区（Swap Area）的管理。本实验假定物理内存充足，`alloc_pages` 失败时直接返回 `NULL` 或触发内核 Panic，尚未实现二级存储介质的按需换入换出。
3. **内存碎片紧缩与动态迁移（Memory Compaction & Migration）**：
   在长周期运行的系统中，频繁的分配与释放会导致外部碎片严重，使得系统即便拥有大量零散空闲内存也无法分配一个稍大的连续物理块。现代 OS 通过暂停进程、拷贝物理页并同步更新页表映射来实现内存块的动态搬移与紧凑，ucore 目前不具备内存迁移能力。
4. **虚拟内存写时复制（Copy-on-Write, COW）**：
   进程创建（`fork`）时不立即为子进程分配新的物理页，而是将父子进程的页表均标记为只读并共享物理页，直至写入发生时由缺页异常驱动真正分配与拷贝。该机制是现代操作系统的性能灵魂，将在后续虚存与进程实验中逐步展开。

## 6.2 AI 协作开发的经验与工程感悟

在本阶段的物理内存管理开发与理论推演中，团队成员深度运用终端 Agent（Claude Code、Antigravity CLI）与 IDE 插件（Cursor、GitHub Copilot）进行协同，沉淀出以下关键工程范式：

### 1. 契约驱动开发（Contract-Driven Development）是防范底层指针崩溃的核心屏障
操作系统内核开发充斥着无类型强转、裸指针算术偏移（如 `le2page`、`pa2page`、`KADDR`、`PADDR`）与位掩码操作。若直接向 AI 提出泛化的实现需求，极易生成看似合乎语法但在边界场景（如地址回卷、非页对齐、结构体填充开销）下崩溃的代码。
通过推行标准四段式契约（`[PROMPT]` / `[RELY]` / `[GUARANTEE]` / `[SPECIFICATION]`），严格将上下文限定在内核已有的头文件声明中，并使用自动化脚本 `check-rely.py` 强制做引用真实性校验，从源头上切断了 AI 凭空臆造虚假宏或成员变量的可能。

### 2. 严格的文件级所有权隔离（Hard Execution Boundaries）是多人多 Agent 协同的底线
当多个团队成员各自配备自主性极强的 AI Agent 时，Agent 倾向于为解决当前问题而擅自修改全局文件（例如私自修改公共的 `code/kern/mm/pmm.c`、`Makefile` 或其他人的报告 section）。
我们在项目根目录通过 `.handoff/STATUS.md` 与规约文件（如 `ANTIGRAVITY.md`）明确划定每个成员的“专属读写白名单”与“安全红线（Red Line）”：禁止越权修改代码、禁止未经授权执行 `git push`、改动依赖接口必须在留言区留痕。这种工程约束保证了团队在高度并行的开发节奏下，至今未发生一次合并冲突或覆盖事故。

### 3. 坚持“答辩防御性思维（Defense-Readiness）”，人必须对代码负全责
AI 生成的代码与推导论述必须经过成员的逐行代码走读与数学公式推导。例如在 First-Fit 与 Best-Fit 的空闲块合并中，相邻性判定必须明确到 $p + p\text{->property} == base$ 的严格数学推导，绝不接受“黑盒能跑通就行”。只有团队成员自己能向答辩老师清晰解释每一行指针运算背后的物理内存状态变化，AI 才能真正成为提升研发效能的加速器，而非掩盖理解缺陷的借口。

### 4. 统一基础设施环境是避免“幽灵排障”的关键
在多平台（WSL2 / Linux / Windows）与多版本模拟器混合的环境下，不同版本 QEMU/OpenSBI 的固件跳转行为差异可能消耗数小时去排查一个压根不存在的内核逻辑 bug。全组统一规范并编译调试版 QEMU 4.1.1，固化了底层硬件仿真基准，使得整个开发过程的精力能够 100% 聚焦于操作系统核心算法与机制设计本身。
