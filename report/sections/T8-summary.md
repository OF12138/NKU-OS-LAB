# 六、实验总结与收获

## 6.1 对操作系统的理解（初稿）

> **【协作边界声明】**：本小节由 nagilix（刘昀皓）基于全组当前阶段性技术实现与理论分析起草初稿；组员 lyp（李云鹏）将在 T6 阶段结合 Best-Fit 与 Buddy System 的最终评测做进一步深度对照与补充扩展。

物理内存管理是操作系统内核所有高级机制（虚存抽象、进程地址空间隔离、缺页异常处理、内核小对象缓存）的硬件基石。通过本实验的动手实现与分析，我们建立了从裸机物理内存抽象为离散数据结构、多策略分配回收以及硬件 MMU 协同的系统性认知：

### 1. 实验核心知识点与 OS 原理的映射对照

| 实验知识点 | 对应 OS 原理概念 | 含义、关系与设计差异分析 |
| :--- | :--- | :--- |
| **`struct Page` 描述符数组** | **物理页帧管理（Frame Management）** | **含义**：将物理内存按固定大小（4KB）切分为页帧，用内存开头的结构体数组一一跟踪每个页的状态。<br/>**关系与差异**：OS 原理中通常抽象为位图（Bitmap）或空闲链表；ucore 在 [`code/kern/mm/memlayout.h`](file:///home/nagilix/Code/NKU-OS-LAB/code/kern/mm/memlayout.h#L34-L39) 中采用固定尺寸数组，占用物理内存开销约占受管内存的 $0.97\%$（每 4096 字节对应 40 字节描述符），通过线性映射下标偏移完成 $O(1)$ 指针换算，较传统位图支持更丰富的引用计数（`ref`）与复合标志位（`flags`）。 |
| **First-Fit / Best-Fit 分配算法** | **连续物理内存动态分配（Contiguous Allocation）** | **含义**：在未开启按需分页机制下，为内核申请多个物理地址连续的页面。<br/>**关系与差异**：First-Fit 优先选择首个匹配块（速度较快但低位碎片集中），Best-Fit 遍历全链表寻找最小合适块（保留大块但易产生极小无法利用的外碎片）。两者在 ucore 中均通过双向循环链表实现，且**仅链接空闲块的首页节点**，释放时依赖物理地址相邻性判定执行 $O(1)$ 双向合并。 |
| **Buddy System 伙伴系统** | **二叉树指数级内存切分（Buddy Allocation）** | **含义**：以 $2^k$ 阶块为单位组织空闲内存，通过二分拆解与伙伴异或算术合并快速响应分配与释放请求。<br/>**关系与差异**：相较于 First-Fit 的 $O(N)$ 链表线性遍历，伙伴系统的分配与合并复杂度降为 $O(\log N)$ 或 $O(1)$，极大抑制了外部碎片，但会引入一定程度的内部碎片（向上取整至 2 的幂次）。 |
| **SLUB / Slab 小对象分配器** | **内核细粒度对象缓存机制（Object Caching）** | **含义**：针对内核小数据结构（数十至数百字节）的频繁申请与释放，在物理页内部划分定长对象池。<br/>**关系与差异**：OS 原理强调以页（4KB）为统一管理单位，但内核直接按页分配极小结构体将造成高达 $90\%$ 以上的内部碎片。本实验中，openfar 在 [`code/kern/mm/slub.c`](file:///home/nagilix/Code/NKU-OS-LAB/code/kern/mm/slub.c) 中实现的 SLUB 采用两层解耦架构：第一层复用底层页分配器（如 Best-Fit），第二层在单物理页首部维护 48 字节元数据（[`struct slab`](file:///home/nagilix/Code/NKU-OS-LAB/code/kern/mm/slub.h#L17-L24)），通过页内单向指针链表管理覆盖 16B～1024B 的 7 级定长通用缓存池。利用 `ROUNDDOWN(addr, PGSIZE)` 即可由任意对象指针常数级计算出 Slab 头，既避免了侵入修改 `struct Page` 结构体，又与底层 `pmm_manager` 及自动化评测保持完全解耦。 |
| **Sv39 分页与高半核映射** | **虚拟内存保护与多级页表（Paging & MMU）** | **含义**：利用硬件 MMU 的三级页表实现 39 位虚拟地址到 56 位物理地址的转换。<br/>**关系与差异**：操作系统通过 `va_pa_offset` 实现内核虚存空间的线性映射，使得 S 态内核能够在保护模式下自由访问受管物理内存，而无需频繁重构页表项。 |

### 2. OS 原理中核心但本实验尚未涉及的高级机制

1. **反向映射机制（Reverse Mapping, rmap）**：
   在真实操作系统（如 Linux）中，一个物理页可能同时被多个进程的虚拟页表（PTE）映射（例如动态共享库或共享内存）。当系统需要回收或换出该物理页时，必须能够从 `Page` 结构体快速反向查找到所有引用它的进程页表项并将其无效化。ucore 当前阶段仅记录了简单的引用计数 `ref`，未构建反向链表（`anon_vma` / `address_space`）。
2. **页面置换与换页机制（Page Replacement & Swapping）**：
   OS 原理中的缺页异常处理（Page Fault Handler）、LRU / Clock 页面置换算法、工作集模型（Working Set）以及交换分区（Swap Area）的管理。本实验假定物理内存充足，`alloc_pages` 失败时直接返回 `NULL` 或触发内核 Panic，尚未实现二级存储介质的按需换入换出。
3. **内存碎片紧缩与动态迁移（Memory Compaction & Migration）**：
   在长周期运行的系统中，频繁的分配与释放会导致外部碎片严重，使得系统即便拥有大量零散空闲内存也无法分配一个稍大的连续物理块。现代 OS 通过暂停进程、拷贝物理页并同步更新页表映射来实现内存块的动态搬移与紧凑，ucore 目前不具备内存迁移能力。
4. **虚拟内存写时复制（Copy-on-Write, COW）**：
   进程创建（`fork`）时不立即为子进程分配新的物理页，而是将父子进程的页表均标记为只读并共享物理页，直至写入发生时由缺页异常驱动真正分配与拷贝。该机制是现代操作系统的性能灵魂，将在后续虚存与进程实验中逐步展开。

## 6.2 AI 协作开发的工程范式与深度反思

在本阶段物理内存管理模块的系统研发与理论推演中，团队成员深度引入终端自主智能体（Claude Code、Antigravity CLI）与代码生成代理（Codex）展开全生命周期协同。面对操作系统内核级裸机代码对指针算术、内存边界和硬件异常的高敏感性，团队摒弃了“黑盒提问-直接复制”的业余使用方式，构建起高可靠、可审计的专业级 AI 辅助系统开发工程范式：

### 1. 基于严密类型约束与双向契约的前验驱动开发（Formal Contract-Driven Engineering）
操作系统内核处于特权级执行环境，充斥着无类型指针转换（如 `(void *)`）、宿主结构体反向寻址（`le2page` 容器宏）与高低半核虚拟地址平滑折算（`va_pa_offset`）。直接使用自然语言提示大模型极易引发基于概率采样的“幻觉缺陷”（如凭空引入虚假宏、假定存在额外链表指针、产生未对齐步长）。
团队在工程实践中全面推行标准化四段式技术契约（`[PROMPT]` / `[RELY]` / `[GUARANTEE]` / `[SPECIFICATION]`）：
- 在 `[RELY]` 契约中，强制原样注入内核经编译器校验的头文件最小上下文，禁止模型假定外部运行时；
- 引入自动化静态校验脚本 `check-rely.py` 作为门禁，逐行校验 AI 可见上下文的代码真实性；
- 在 `[SPECIFICATION]` 契约中引入形式化前置条件（Pre-Condition）、后置条件（Post-Condition）与边界用例（Cases），将大模型的生成空间严格收敛至满足系统不变性（Invariants）的有界空间。

### 2. 多自主智能体并发环境下的硬边界所有权隔离机制（Hard Execution Boundaries & Distributed Concurrency Control）
在多人多 Agent 高频迭代的工程背景下，每个自主智能体均具备强大的全局文件搜索与跨目录编辑能力。若缺乏确定性隔离，智能体往往会为解决局部依赖而擅自改动全局公共文件（如擅自改动 `pmm.c`、`Makefile` 或覆盖他人的报告章节），引发毁灭性的隐蔽冲突。
团队在架构上设计了严格的“文件级所有权隔离模型”：
- 通过 `.handoff/STATUS.md` 与本地规约配置文件（如 `ANTIGRAVITY.md`）明确定义每位成员及其 Agent 的“绝对写入白名单”与“不可逾越的安全红线（Red Line）”；
- 严禁越权修改非负责范围内的 `code/` 与报告章节，依赖接口变更必须在 `.handoff/tasks/` 异步留言留痕；
- 实施非重叠的模块交付解耦（如 nagilix 聚焦分析与公共文档，openfar 负责内核集成，lyp 负责核心分配算法），确保了分布式多 Agent 并行开发下的零合流冲突。

### 3. 基于数学不变量证明与代码走读的“答辩防御性验证（Defense-Readiness Verification）”
团队始终坚持“人类工程师对内核执行流承担最终责任”的底线原则，坚决反对将通过测试用例作为代码可接受的唯一判据。
针对 AI 生成的核心逻辑，团队执行逐行指令级代码走读与算法不变量推导：
- 例如在 First-Fit 与 Best-Fit 连续物理块的双向合并中，必须推导出严格的物理相邻性判定公式：向低地址合并必须严格满足 $p + p\text{->property} == base$，向高地址合并必须严格满足 $base + base\text{->property} == p$；
- 每一处指针移动与位操作，均要求团队成员能够在不借助 AI 的前提下向课程答辩组清晰阐述其在物理内存空间与 Page 描述符数组中的拓扑映射变化；
- 将 AI 明确界定为算法实现探索的加速器与自动化边界用例生成的对手机构，而非替代系统机理深度理解的认知外包工具。

### 4. 消除微体系结构与固件差异的确定性底层仿真基准（Deterministic Hardware Virtualization Baseline）
在跨宿主操作系统（WSL2 / Linux / Windows）与多模拟器版本的异构协作环境中，不同版本 QEMU/OpenSBI 的固件加载行为（如 OpenSBI v0.4 的 `fw_jump` 与 v1.3 的 `fw_dynamic` 对 0x80200000 跳转地址的处理差异）会产生表现各异的虚假系统崩溃，极易导致团队陷入耗时耗力的“幽灵排障”。
团队通过编写统一编译脚本固化了专属的带调试信息 QEMU 4.1.1 仿真基准，并在 Makefile 中通过环境变量重定向绑定运行实例：
- 将硬件仿真环境与底层固件抽象为团队共享的确定性黑盒；
- 保证了 AI 在排查汇编跳转、页表解析与中断异常时面对的是统一且确定的硬件执行规范，彻底阻断了因模拟器版本分歧引入的工程排障噪声。
